# KCC Marine Cloud V9.3 — Invitation regression rollback/fix

## Root cause found by comparing V9.2 with the known-good V8

V8 invitation delivery did **not** query the `profiles` table before generating the Supabase Auth link. It generated the Auth invite/magic link directly, then delivered it through Resend.

V9 introduced a new pre-flight credential-state lookup:

```ts
.from('profiles').select('id,password_set_at').eq('email', email)
```

That made invitation delivery depend on the new `password_set_at` database migration. If the frontend was deployed before that migration existed in the production Supabase database, invitation delivery failed *before Resend was even called*, typically with a credential-state/database error. This explains why the old V8 continued to send correctly while the newer release did not.

V9.2 also added a Supabase Auth email fallback. This added a second transport path that was not part of the known-good production flow and made provider failures harder to diagnose.

## V9.3 fix

- Restores the proven V8 identity-link flow: `auth.admin.generateLink(invite)` -> existing-user `magiclink` fallback -> branded Resend email.
- Removes the invitation-time dependency on `profiles.password_set_at` entirely.
- Does not require the V9 credential-state SQL migration for invitation email delivery.
- Keeps explicit Auth metadata (`password_setup_required/password_setup_complete`) for genuinely new accounts.
- Existing/legacy users without this explicit metadata are not forced through first-time password setup.
- If the first email attempt fails after Auth created the identity, resend uses magiclink but still sees the explicit setup metadata and sends the new user to password creation.
- Removes the V9.2 Supabase SMTP fallback from organization invitations. Resend is again the single explicit mail transport, matching the previously working architecture.
- If Resend fails, the exact provider error is surfaced and the secure manual URL is retained for emergency use.

## Production environment required (same as the working V8)

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `RESEND_API_KEY`
- `AUTH_FROM_EMAIL=KCC Marine Cloud <sender@verified-resend-domain>`
- `NEXT_PUBLIC_SITE_URL=https://marine.kccorpglobal.com` (or the actual production URL)

`AUTH_FROM_EMAIL` must belong to a domain verified in the same Resend account as `RESEND_API_KEY`.

## First tests

1. Existing KCC Admin logs in with password — no onboarding.
2. Invite a brand-new technician — email arrives via Resend, recipient creates password, enters `/today`.
3. Invite a brand-new company owner — email arrives, creates password, enters `/company`.
4. Invite an existing Marine Cloud user to another organization — same account is reused; no duplicate Auth user.
5. Resend a failed new-user invite — email arrives and still requires password setup.
6. Temporarily set a bad sender in a non-production preview to confirm the UI shows the real Resend provider error instead of a generic credential-state error.

## Important deployment note

The V9 database migrations are still useful for the broader auth UX, but invitation delivery no longer depends on them. Apply migrations normally; do not let a frontend deployment get blocked from sending invitations merely because a UX marker column has not reached production yet.
